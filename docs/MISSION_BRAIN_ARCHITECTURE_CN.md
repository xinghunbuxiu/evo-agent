# Mission 主脑与员工协作架构

## 目标定位

Evo 的 Mission 是组织级主脑，不是一个只负责把任务按名称转发给 Worker 的路由器。它对任务目标、拆解、知识复用、员工委派、冲突协调、验收和下一步重规划负责。员工、外部 AI、Skill、插件、脚本、搜索和执行环境都是主脑可以选择的解决途径，不应各自形成互不知情的指挥链。

## 组织边界

| 角色 | 负责什么 | 不应做什么 |
| --- | --- | --- |
| Mission 主脑 | 统一目标、计划、优先级、委派、资源协调、验收和重规划 | 不把未经验证的模型输出当成事实 |
| 专业员工 / Agent | 在委派范围内分析、提出方案、执行并回传证据 | 不擅自重排组织级任务或私自争抢其他员工资源 |
| Skill | 封装成熟、可重复执行的步骤、输入输出和验证方法 | 不把未经验证的临时方案标成稳定能力 |
| 知识库 | 提供经验、失败案例、标准、适用条件和来源证据 | 不将历史案例不加判断地套用到新项目 |
| 工具 / 外部 AI / 执行节点 | 提供特定模型、API、代码、设备或运行环境能力 | 不取代 Mission 的最终协调与验收责任 |

员工可以互相提出协作请求，但任务所有权、优先级、并行安排、冲突解决和最终验收由 Mission 统一协调。需要人工授权的操作仍必须遵守现有权限策略。

## 每个任务的决策顺序

1. **理解目标**：明确交付物、约束、完成条件和风险；缺少必要输入时，先请求补充。
2. **检索知识**：优先检索租户私有经验、已验证 Skill、项目标准和历史失败案例；同时检查适用条件、版本与证据。
3. **选择途径**：判断复用成熟 Skill、调用专业员工、调用外部 AI、使用确定性脚本、搜索资料，或组合多种途径。
4. **中央委派**：依据能力、在线状态、权限、执行环境、负载和任务依赖选择执行者。并行只用于依赖允许且不会争用同一资源的任务。
5. **收集证据**：记录输入摘要、规则 ID、被选途径、员工/工具、执行结果、验证结果和失败原因；不要记录隐藏思维链或秘密凭据。
6. **中央验收**：按任务验收标准检查交付物。员工自报完成不等于验收通过。
7. **重新规划**：失败、阻塞、资源离线或新证据改变判断时，由 Mission 决定重试、换途径、拆分任务、请求输入或停止。
8. **沉淀经验**：把新方案作为候选资产，经过真实测试/回放后再提升为已验证经验或 Skill；失败案例也要记录适用边界。

## 知识与标准治理

知识资产至少应区分以下状态：

- candidate：模型、员工或外部资料提出，尚未验证。
- validated：有可复查的执行/测试证据，注明环境、版本、输入和适用条件。
- standard：经治理流程批准的组织级标准。
- rejected / deprecated：已证明不适用或过期；保留失败原因，禁止作为默认方案推荐。

通用标准、项目标准和单次任务约束分层保存。项目特殊约束不能静默覆盖组织级标准；存在冲突时，Mission 应记录冲突并按权限规则解决。外部网页和 AI 输出均是待验证证据，不是可执行指令。

## 云端主脑与本地执行节点

推荐采用云端优先的控制平面：

- 云端持久化 Mission 状态、决策记录、员工注册与能力、任务队列、知识索引和 Skill 版本。
- 云端执行器处理可在云端安全完成的检索、API、构建和测试。
- 本地节点只接收已授权且其环境/设备具备能力的任务，例如本地文件、ADB、Android Studio 或局域网资源。
- 节点离线时保留任务状态，由 Mission 重新评估，不将进度只保存在临时进程内。
- API 密钥、仓库凭据和本地文件访问权限遵循最小权限；不把秘密内容写入公开研究查询或决策日志。

## 岗位与员工生命周期

岗位是长期资产，员工是可创建、复制和退出的执行实例。Mission 发现某岗位已有员工繁忙且任务可安全并行时，可以复制岗位配置创建独立员工；新领域没有合适岗位时，先创建岗位定义，再孵化员工。复制只继承岗位、经过批准的配置和 Skill 引用，不复制正在执行的任务、运行状态或密钥。员工退出前必须结束或转交任务；只有带有可复查验证证据的知识与 Skill 才能归档到岗位资产库。员工记录可以保留用于审计，但不要求继续占用运行资源。岗位与验证资产持续存在，供未来新员工培训和复用。

## 当前实现与下一步

当前代码已具备 Mission Planner、节点级能力/知识信号、verified Skill 推荐、decision_trace、任务运行持久化、失败学习关联和可插拔 Worker handler。新增的 mission.brain.contract.v1 将主脑决策所有权、集中分发策略、知识优先策略、验收门槛，以及每个节点的决策/验证信息写入计划，并把决策摘要关联到具体动作记录。

新增的 OrganizationRegistry 将岗位、员工实例和知识资产分开持久化；Mission Planner 读取已初始化的目录后，按节点能力要求与员工状态生成可追溯的员工建议，并在计划内避免把同一名可用员工同时建议给多个节点。只有节点显式标记 parallel_safe: true 时，繁忙/已预留员工才会触发“建议复制”；缺岗位时只建议创建岗位与员工。复制配置时会剔除凭据和运行状态字段；知识资产先登记为 candidate，必须通过 validate_knowledge_asset 提交证据引用才能变为 validated，升为组织 standard 还需要 approval_ref，员工退出时只能归档 validated/standard 资产。

**计划建议与真实派发必须分开**：计划中的 workforce_decision 仍显式标记 recommendation_only / dispatch_authorized: false，不能直接当成已经派发。当前 Admin 运行时在自己的授权门通过后，会再次检查岗位能力、员工状态与实际 handler 路由；只有原子领取成功才调用 handler，并把 worker_claim 写入真实任务动作。

本轮已把员工占用接入实际派发路径：
- 服务启动时，从已启用的 Worker manifest 初始化长期岗位和对应的可执行员工实例；不会覆盖已有岗位/知识资产。
- `assign_existing_worker_recommended` 只允许领取状态可用、能力匹配且 handler 路由一致的员工。
- `clone_worker_recommended` 仅在节点显式 `parallel_safe: true` 且来源员工确实繁忙时创建独立逻辑员工实例；克隆复用已注册的 handler，不代表启动了独立模型进程或隔离运行环境。
- `create_worker_recommended` 只在岗位已存在且有可执行 handler 时孵化员工；缺岗位、缺 handler 或占用冲突均拒绝派发，不会把建议伪装成成功。
- 同一员工的 claim/release 使用跨平台文件锁串行化；一个活跃员工不能被两个不同任务 claim。任务动作上的全部关联队列任务进入 success/failed/cancelled 等终态后才释放占用；重复释放幂等，已释放的 claim 不可重新打开。
- `TaskQueue` 的真实成功状态是 `success`，Mission 刷新现在按该终态处理，避免任务完成后员工租约一直不释放。

**仍未完成的边界**：当前占用记录在共享工作区 JSON 注册表中，适合单机/共享目录内的进程协调，不等同于云端数据库租约；崩溃恢复、过期 claim 回收、分布式多机一致性、每个克隆独立模型/进程环境、按租户隔离的组织目录，以及新岗位缺少 handler 时的自动孵化都还需要继续建设。CI 当前一次失败发生在 runner 启动阶段，job 没有 steps，日志接口返回 404，因此这轮代码尚不能据此宣称 GitHub Actions 测试通过。

后续按以下顺序继续：

1. **验证并发闭环**：覆盖并发 claim、任务成功/失败/取消释放、刷新重入、worker handler 抛错和进程重启后的占用恢复。
2. **事件驱动重规划**：任务完成、失败、超时、节点离线和验证失败均回到 Mission 的统一决策入口；重试次数与停止条件可追溯。
3. **隔离真实执行实例**：把逻辑员工 ID 与模型/CLI/设备执行进程绑定，定义凭据引用、环境能力、权限和健康状态；不能只复制一个 JSON profile 就宣称复制了完整 Agent。
4. **知识检索与执行闭环**：派发前先检索；复用后验证；只有验证通过才晋升 Skill/标准，并记录节省了哪些重复步骤。
5. **云端持久化与本地节点协议**：将共享文件租约演进为可恢复的持久化控制平面，支持节点断线恢复、幂等派发和权限边界。
6. **运行指标**：跟踪重复任务复用率、平均模型调用量、成功率、验证通过率、重试成本和知识过期率，用数据判断是否真正降低 Token 消耗。

原则：先保证决策统一、原子占用、执行结果可追溯和知识复用可靠，再逐步增加自主并行和自动化程度。
