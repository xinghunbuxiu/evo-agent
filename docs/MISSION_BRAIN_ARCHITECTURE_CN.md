# Mission 主脑与员工协作架构

## 目标定位

Evo 的 Mission 是组织级主脑，不是一个只负责把任务按名称转发给 Worker 的路由器。它对任务目标、拆解、知识复用、员工委派、冲突协调、验收和下一步重规划负责。员工、外部 AI、Skill、插件、脚本、搜索和执行环境都是主脑可以选择的解决途径，不应各自形成互不知情的指挥链。

## 组织边界

| 角色 | 负责什么 | 不应做什么 |
| --- | --- | --- |
| Mission 主脑 | 理解目标、拆分任务、管理依赖与优先级、定义验收、跟踪执行、处理任务级重规划；向育成师提出人员需求；校验人员安排后发出受控执行授权 | 不代替育成师做人事管理、员工画像、培养和岗位调配；不把未经验证的模型输出当成事实 |
| 育成师（Talent Center） | 创建/孵化员工、维护员工画像与能力档案、岗位匹配、人员安排与调度、带教训练、能力考核、晋升/转岗/退休；接收 Mission 的人员需求并确认由谁承担 | 不擅自修改 Mission 的任务依赖、优先级和验收标准；不绕过 Mission 直接启动任务执行 |
| 专业员工 / Worker | 在岗位与授权范围内分析、提出方案、执行任务、回传结果和证据；通过实战、辅导和考核持续成长 | 不擅自重排组织级任务或私自争抢其他员工资源；不自行宣称能力已通过考核 |
| Skill | 封装成熟、可重复执行的步骤、输入输出和验证方法 | 不把未经验证的临时方案标成稳定能力 |
| 知识库 | 提供经验、失败案例、标准、适用条件和来源证据 | 不将历史案例不加判断地套用到新项目 |
| 工具 / 外部 AI / 执行节点 | 提供特定模型、API、代码、设备或运行环境能力 | 不取代 Mission 的任务协调与最终验收责任 |

**双重边界**：Mission 拥有任务决策权（做什么、拆成什么、依赖如何安排、怎样验收）；育成师拥有人才管理权（谁来做、员工如何培养、何时晋升或调整岗位）。育成师确认人员安排后，Mission 仍负责检查任务授权、能力/权限、执行器路由和 Worker 原子占用，再实际提交执行。人员选择与技术执行授权不是同一件事。

## 每个任务的决策顺序

1. **理解目标**：明确交付物、约束、完成条件和风险；缺少必要输入时，先请求补充。
2. **检索知识**：优先检索租户私有经验、已验证 Skill、项目标准和历史失败案例；同时检查适用条件、版本与证据。
3. **选择途径**：判断复用成熟 Skill、调用专业员工、调用外部 AI、使用确定性脚本、搜索资料，或组合多种途径。
4. **提出人员需求**：Mission 根据拆解后的节点生成 staffing request，明确能力要求、交付物、风险、依赖、时限、是否适合训练和是否允许并行；Mission 不在这一步创建或管理员工。
5. **育成师安排人员**：Talent Center 结合员工画像、已验证能力、历史表现、当前负载、成长目标和岗位要求，选择现有员工；必要时创建岗位/孵化员工、安排导师或制定训练任务，并记录可审计的 staffing assignment。不能只凭模型自评能力派人。
6. **受控执行与收集证据**：Mission 校验 staffing assignment 与任务/租户/员工/Worker 的绑定，重新检查权限、执行器路由、员工可用状态和并发安全，再原子领取 Worker 并提交队列。记录人员安排、授权、执行结果、验证结果和失败原因；不要记录隐藏思维链或秘密凭据。
7. **验收与双线复盘**：Mission 按任务验收标准检查交付物，员工自报完成不等于验收通过；育成师根据同一份客观证据更新员工画像、识别能力缺口并决定辅导/训练/晋升。任务结果与员工成长结果分开记录。
8. **重新规划与沉淀**：任务失败时，Mission 负责当前任务的诊断、重试、拆分、换工具或停止；育成师负责判断是否继续培养原员工、安排资深员工带教或调整人员。默认优先让原员工在辅导后再次实践，不因一次失败直接淘汰或换人。通过验证的方案才能晋升为经验或 Skill。

## 育成师管理的人员模型与职责闭环

产品中的“员工”不是一个临时 Worker 进程，应区分四类对象：

- **岗位 / Work Type / Role**：长期岗位定义，描述职责、所需能力、标准和可执行工种路由。
- **员工档案 / Employee Member**：长期人员身份，保存人格、长期目标、岗位经历、能力画像、训练计划、成长状态和带教关系。
- **Worker 实例**：实际执行资源，绑定可用 handler、模型/CLI/设备环境与任务租约；一个员工可以关联一个或多个 Worker 实例。Worker 忙碌、离线或被回收，不等于员工被淘汰。
- **育成师 / Talent Center**：管理岗位与员工生命周期，负责孵化、画像、匹配、排班/调度、辅导、训练、考核和晋升；其专业知识可按工种/能力域扩展，不要求一开始就拆成多个独立育成师 Agent。

现有实现已经有两类持久化对象：`child_members` 保存员工身份、人格、训练与成长信息；`OrganizationRegistry` 在 `.organization/` 保存 Role、Worker 和知识资产，并通过员工/租户 ID 及 `instance_runtime.organization_worker_ids` 建立关联。后续必须把这条关联作为正式生命周期契约：创建员工、绑定 Worker、克隆执行实例、调岗、退休和恢复都要可追踪、幂等，并且不能出现员工档案与执行目录互相脱节。

### 失败后的职责分工

- Mission 判断“当前任务下一步怎么解决”，对任务结果负责。
- 育成师判断“这个员工怎样才能学会”，对员工成长负责。
- Worker 是学习和实践的主体，不是失败一次就被替换的临时消耗品。
- 育成师可以安排同伴协作或导师带教，但应保留原员工的任务/训练 lineage；只有能力不匹配、权限不足、风险过高或培养预算耗尽时，才提出转派。
- 员工能力变化必须由真实任务、训练考核和独立验证证据驱动；不能仅凭模型生成的画像或一次成功自评升级。

## 知识与标准治理

知识资产至少应区分以下状态：

- candidate：模型、员工或外部资料提出，尚未验证。
- validated：有可复查的执行/测试证据，注明环境、版本、输入和适用条件。
- standard：经治理流程批准的组织级标准。
- rejected / deprecated：已证明不适用或过期；保留失败原因，禁止作为默认方案推荐。

通用标准、项目标准和单次任务约束分层保存。项目特殊约束不能静默覆盖组织级标准；存在冲突时，Mission 应记录冲突并按权限规则解决。外部网页和 AI 输出均是待验证证据，不是可执行指令。

## 云端主脑与本地执行节点

推荐采用云端优先的控制平面：

- 云端持久化 Mission 状态、决策记录、员工注册与能力、任务队列、知识索引和 Skill 版本。
- 云端执行器处理可在云端安全完成的检索、API、构建和测试。
- 本地节点只接收已授权且其环境/设备具备能力的任务，例如本地文件、ADB、Android Studio 或局域网资源。
- 节点离线时保留任务状态，由 Mission 重新评估，不将进度只保存在临时进程内。
- API 密钥、仓库凭据和本地文件访问权限遵循最小权限；不把秘密内容写入公开研究查询或决策日志。

## 岗位与员工生命周期

岗位是长期资产，员工是可创建、复制和退出的执行实例。Mission 发现某岗位已有员工繁忙且任务可安全并行时，可以复制岗位配置创建独立员工；新领域没有合适岗位时，先创建岗位定义，再孵化员工。复制只继承岗位、经过批准的配置和 Skill 引用，不复制正在执行的任务、运行状态或密钥。员工退出前必须结束或转交任务；只有带有可复查验证证据的知识与 Skill 才能归档到岗位资产库。员工记录可以保留用于审计，但不要求继续占用运行资源。岗位与验证资产持续存在，供未来新员工培训和复用。

### 当前差距与实施顺序（按产品职责恢复主线）

当前已经具备员工建档/画像字段、同岗位复制、育成师带教履历、训练复盘入口、岗位/Worker 注册表、能力匹配建议、原子 claim/release 和 Mission 执行证据。**这些是已有资产，不重新造轮子。**

但目前 Mission Planner 产生的 `workforce_decision` 是 recommendation-only，Mission runtime 在自己的授权门内可直接按推荐结果领取/孵化 Worker 并派发；还没有形成“Mission 提出人员需求 → 育成师确认人员安排 → Mission 执行授权”的强制业务闭环。员工档案与 Worker 注册表也仍是两个存储边界，需要进一步统一生命周期操作。带教履历已有，但失败证据自动转成针对该员工的训练计划、训练实践、独立考核，再回到原任务重试的链路尚未证明完整。

实施顺序：

1. **人员身份与档案接线**：明确 Employee Member ↔ Role ↔ Worker 的主外键和租户边界；创建/克隆/绑定/退休均通过统一服务完成；不再让 UI 或 Mission 各自拼接两套档案。
2. **Mission staffing request**：每个需要人员的 Mission 节点产生结构化人员需求；记录所需能力、handler、风险、并行限制和验收要求。
3. **育成师 staffing assignment**：提供候选员工、匹配理由、负载和培养机会；育成师确认/调整人员，允许安排导师或协作员工；未确认的任务不得以“已分派”状态执行。
4. **Mission 受控派发**：只接受已批准且未过期的 assignment；再次检查 tenant、任务节点、岗位能力、Worker handler、可用状态和 lease；重复提交幂等。
5. **员工失败培养闭环**：任务失败回传育成师；生成员工专项诊断与训练计划；原员工完成训练/带教后回到原任务重新实践；Mission 独立验收；超过培养预算再转派或请求人工决策。
6. **成长考核与可视化**：能力等级由可追溯证据更新；员工工作台显示画像变化、训练进度、错题本、Skill 和晋升条件；育成师工作台显示人才池、待安排人员需求、负载、训练队列和考核结果。

首个可验收纵向切片：创建一名员工并绑定一个可执行 Worker → Mission 拆出任务并生成 staffing request → 育成师确认该员工 → Mission 授权并执行 → 故意制造一次失败 → 育成师训练原员工 → 原员工再次执行 → Validator 通过 → Mission 关闭任务且员工画像留下有证据的成长记录。

## 当前实现与下一步

当前代码已具备 Mission Planner、节点级能力/知识信号、verified Skill 推荐、decision_trace、任务运行持久化、失败学习关联和可插拔 Worker handler。新增的 mission.brain.contract.v1 将主脑决策所有权、集中分发策略、知识优先策略、验收门槛，以及每个节点的决策/验证信息写入计划，并把决策摘要关联到具体动作记录。

新增的 OrganizationRegistry 将岗位、员工实例和知识资产分开持久化；Mission Planner 读取已初始化的目录后，按节点能力要求与员工状态生成可追溯的员工建议，并在计划内避免把同一名可用员工同时建议给多个节点。只有节点显式标记 parallel_safe: true 时，繁忙/已预留员工才会触发“建议复制”；缺岗位时只建议创建岗位与员工。复制配置时会剔除凭据和运行状态字段；知识资产先登记为 candidate，必须通过 validate_knowledge_asset 提交证据引用才能变为 validated，升为组织 standard 还需要 approval_ref，员工退出时只能归档 validated/standard 资产。

**计划建议与真实派发必须分开**：计划中的 workforce_decision 仍显式标记 recommendation_only / dispatch_authorized: false，不能直接当成已经派发。当前 Admin 运行时在自己的授权门通过后，会再次检查岗位能力、员工状态与实际 handler 路由；只有原子领取成功才调用 handler，并把 worker_claim 写入真实任务动作。

本轮已把员工占用接入实际派发路径：
- 服务启动时，从已启用的 Worker manifest 初始化长期岗位和对应的可执行员工实例；不会覆盖已有岗位/知识资产。
- `assign_existing_worker_recommended` 只允许领取状态可用、能力匹配且 handler 路由一致的员工。
- `clone_worker_recommended` 仅在节点显式 `parallel_safe: true` 且来源员工确实繁忙时创建独立逻辑员工实例；克隆复用已注册的 handler，不代表启动了独立模型进程或隔离运行环境。
- `create_worker_recommended` 只在岗位已存在且有可执行 handler 时孵化员工；缺岗位、缺 handler 或占用冲突均拒绝派发，不会把建议伪装成成功。
- 同一员工的 claim/release 使用跨平台文件锁串行化；一个活跃员工不能被两个不同任务 claim。任务动作上的全部关联队列任务进入 success/failed/cancelled 等终态后才释放占用；重复释放幂等，已释放的 claim 不可重新打开。
- `TaskQueue` 的真实成功状态是 `success`，Mission 刷新现在按该终态处理，避免任务完成后员工租约一直不释放。

**仍未完成的边界**：当前占用记录在共享工作区 JSON 注册表中，适合单机/共享目录内的进程协调，不等同于云端数据库租约；崩溃恢复、过期 claim 回收、分布式多机一致性、每个克隆独立模型/进程环境、按租户隔离的组织目录，以及新岗位缺少 handler 时的自动孵化都还需要继续建设。CI 当前一次失败发生在 runner 启动阶段，job 没有 steps，日志接口返回 404，因此这轮代码尚不能据此宣称 GitHub Actions 测试通过。

后续按以下顺序继续：

1. **验证并发闭环**：覆盖并发 claim、任务成功/失败/取消释放、刷新重入、worker handler 抛错和进程重启后的占用恢复。
2. **事件驱动重规划**：任务完成、失败、超时、节点离线和验证失败均回到 Mission 的统一决策入口；重试次数与停止条件可追溯。
3. **隔离真实执行实例**：把逻辑员工 ID 与模型/CLI/设备执行进程绑定，定义凭据引用、环境能力、权限和健康状态；不能只复制一个 JSON profile 就宣称复制了完整 Agent。
4. **知识检索与执行闭环**：派发前先检索；复用后验证；只有验证通过才晋升 Skill/标准，并记录节省了哪些重复步骤。
5. **云端持久化与本地节点协议**：将共享文件租约演进为可恢复的持久化控制平面，支持节点断线恢复、幂等派发和权限边界。
6. **运行指标**：跟踪重复任务复用率、平均模型调用量、成功率、验证通过率、重试成本和知识过期率，用数据判断是否真正降低 Token 消耗。

原则：先保证决策统一、原子占用、执行结果可追溯和知识复用可靠，再逐步增加自主并行和自动化程度。
