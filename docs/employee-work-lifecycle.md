# Employee Work Lifecycle（员工工作生命周期）

**Status:** Core design contract  
**Contract:** `employee.work-lifecycle.v1`  
**Applies to:** Mission、Worker、Capability、Skill、Experience，以及所有由员工执行的工作。

## 1. 核心原则

员工不是按固定脚本机械走完若干步骤，而是围绕目标、约束、可用能力和真实反馈完成工作。

统一工作链：

`我要做什么 → 应该怎么做 → 制定计划 → 实时执行计划 → 验证 → Fix/Test 迭代直到 Pass → 复盘 → 经验沉淀 →（必要时）Skill 候选`

这条链是所有员工共同遵循的工作协议，不是每种任务都必须采用相同的具体步骤。**阶段语义统一，阶段内部的动作由任务分析和运行反馈动态决定。**

必须遵守：

1. 以用户目标和真实上下文为起点，不以预设模板替代任务理解。
2. 计划必须来自对目标、交付物、约束、风险、能力和已有经验的分析。
3. 计划是可演进的版本化对象；执行反馈可以触发局部修订或重新规划。
4. 执行状态、测试结果和产物必须来自真实工具/Worker/外部系统回传，不能由 Planner 伪造。
5. Pass 必须由事先明确的验收条件和可核验的验证证据共同支持。
6. 失败后先诊断，再决定修复、补充信息、学习、换能力/员工或停止；不能盲目重复同一动作。
7. 工作结束必须复盘；经验与 Skill 是复盘产物，不是每次任务都强制生成。
8. 安全、权限、租户隔离、资源预算和人工审批优先于“必须跑到 Pass”。无法安全继续时应明确阻塞，不能伪报 Pass。

## 2. 概念边界

| 概念 | 职责 | 不应承担 |
|---|---|---|
| Mission（主脑） | 理解总目标、拆解工作、协调依赖与员工、审查全局结果、决定重规划 | 冒充实际执行者或伪造执行结果 |
| Worker（员工） | 对分配的工作负责，分析方法、制定/更新局部计划、调用能力、执行、验证、修复和复盘 | 未授权调用工具、把未经验证的输出声明为 Pass |
| Capability（能力） | 描述可完成的工作类型、前置条件、输入输出和约束 | 作为执行成功的证据 |
| Tool / Executor（工具/执行器） | 执行一个具体动作并返回真实结果、产物和错误 | 自行决定 Mission 总目标或技能晋升 |
| Skill（技能） | 经验证、可复用的做事方法/程序/工具组合及其适用条件 | 等同于普通提示词、一次性计划或未经验证的代码 |
| Experience（经验） | 记录一次工作中的情境、决策依据、实际动作、结果、偏差、原因和教训 | 仅保存“成功/失败”布尔值 |

Mission 可以委派给 Worker；Worker 可以按权限使用 Capability 和工具。每次委派、调用、验证和复盘都要保留关联 ID，形成可追溯链。Worker 的局部计划必须服从 Mission 目标与约束；局部计划变化应回报主脑。

## 3. 生命周期阶段语义

以下是统一语义边界，不是硬编码的固定步骤列表。某个任务可以在一个阶段内产生多个动态步骤，也可以根据任务性质跳过不适用的子动作，但不能跳过必要的验收和复盘。

### A. Goal Understanding — 我要做什么

形成结构化工作目标：

- 原始目标及规范化目标；
- 预期交付物及其可观察属性；
- 输入、上下文、事实来源和缺失信息；
- 范围、约束、权限、风险和截止条件；
- 成功标准及其可验证方式；
- 当前不确定性、假设和需要澄清的问题。

理解结果应保留来源和置信信息。缺少关键输入时，先请求补充或形成明确假设，不得静默编造。

### B. Approach — 应该怎么做

Worker 根据目标和现有信息形成方法选择：

- 检索可用 Worker、Capability、工具、已验证 Skill 和 Experience；
- 比较候选方法的适用条件、成本、风险和证据质量；
- 识别能力缺口、知识缺口、环境缺口和权限缺口；
- 解释为何选择某条路线，以及为何不选择其他路线；
- 确定需要哪些验证手段。

方法选择必须是任务相关的动态决策。不得把某个行业、任务类型或某个 Worker 的步骤写成所有任务的全局固定流程。

### C. Planning — 制定计划

计划是有版本的执行提案。每个计划版本至少表达：

- 目标与交付物引用；
- 步骤/子任务及其依赖关系；
- 每一步的预期结果、执行者/能力要求和输入；
- 需要的权限、工具、资源和风险控制；
- 验收条件、验证方式及证据要求；
- 失败分支、重试/修复策略和停止条件；
- 计划假设、来源、版本和创建原因。

步骤 ID 在同一计划版本内稳定。计划修订创建新版本，保留旧版本及修订原因；已执行步骤不可被新计划静默改写。计划本身不代表执行已经发生。

### D. Live Execution — 实时执行计划

Worker 按依赖和授权执行当前可执行步骤。每个步骤都应形成运行记录：

- execution / attempt ID；
- mission、worker、plan version、step ID；
- 实际使用的 Capability、Skill 版本和工具；
- 输入/输出摘要及产物引用；
- 开始/结束时间、状态和资源消耗；
- 真实日志、错误和外部回执；
- 与计划的偏差及其原因。

执行过程中允许根据新证据更新计划，但必须留下计划修订事件，并说明受影响的步骤。运行状态必须来自任务队列或执行器的实际状态，不可从计划状态推断。

### E. Verification — 测试与验收

验证不是统一写死的 pytest。验证方法由交付物、风险和验收条件决定，可以是自动化测试、结构校验、人工审核、外部系统回执、对照检查或多种方式组合。

每项验收条件都应能映射到：

- 验收条件 ID 与版本；
- 验证器/验证方法及版本；
- 被检查的产物或执行结果摘要；
- 实际结果、证据引用和验证时间；
- `pass`、`fail`、`inconclusive` 或 `blocked` 结论。

只有所有必需验收条件均通过，且证据完整、可信、未过期，当前交付物才可标记 Pass。没有验证证据不能因为 Worker 自述成功而 Pass。

### F. Fix/Test Iteration — 修复与再验证

当验证为 Fail：

1. 分析失败证据，定位原因和影响范围；
2. 分类为实现错误、计划错误、输入缺失、环境问题、能力不足、权限问题或验收定义问题等；分类应可扩展；
3. 选择修复动作：修改产物、调整方法、补充输入、学习新能力、换工具/Worker、更新计划或请求人工决策；
4. 创建新的 attempt，保留原失败记录；
5. 对受影响验收条件重新验证；必要时执行完整回归验证；
6. 根据新结果继续、重规划或停止。

循环的退出条件不是固定重试次数，而是由验收结果和运行策略决定：

- **Pass：** 必需验收条件全部通过；
- **Need input：** 需要外部补充信息；
- **Blocked：** 权限、依赖、环境或安全条件不满足；
- **Escalated：** 超出 Worker 授权或需要人工决策；
- **Budget exhausted：** 达到该任务策略配置的时间、成本、尝试次数或资源预算；
- **Cancelled：** 任务被合法取消。

预算是运行策略参数，不是代码中针对某种任务写死的常量。达到预算不得伪造 Pass；应输出当前证据、未通过项和建议的下一步。对同一失败原因重复执行无变化动作，应触发重新诊断，而不是无限重试。

### G. Reflection — 最后复盘

复盘基于计划、执行事件、验证证据和产物，而不是仅凭最终结果。至少回答：

- 目标是否真正完成，证据是什么；
- 计划哪些判断正确，哪些不正确；
- 实际路径与计划有何偏差，为什么；
- 哪些动作有效、无效、重复或遗漏；
- 失败的根因是什么，修复是否消除了根因；
- 哪些信息/能力/工具/权限仍然不足；
- 下次遇到类似情况应保留、改变或避免什么。

复盘要区分事实、推断和建议；保留来源引用与置信度。失败任务同样必须复盘，不能只学习成功案例。

### H. Experience / Skill — 经验沉淀与必要时生成技能

每次完成或终止的工作都应产生 Experience（可配置隐私和保留策略）。经验应包含情境、目标、计划版本、关键决策、实际执行、验证证据、偏差、根因、修复、结果和可迁移教训。

只有满足复用条件时才创建 Skill 候选，例如：

- 方法在明确适用范围内可重复使用；
- 输入、输出、前置条件和权限边界可描述；
- 步骤或程序足够明确，可由相应执行/指导机制消费；
- 有真实执行与验证证据；
- 已知失败边界和风险；
- 不包含租户私有数据、密钥或不可共享内容。

Skill 候选不等于已验证 Skill。验证、签名、发布和跨租户共享必须经过独立授权流程。一次成功、历史经验聚类或模型生成的步骤文本都不能单独证明 Skill 有效。

## 4. 运行事件与可追溯性

事件是生命周期的事实来源。建议统一事件封装，具体业务字段按事件类型扩展：

- `schema_version`、`event_id`、`event_type`、`occurred_at`；
- `tenant_id`、`mission_run_id`、`worker_id`；
- `plan_id`、`plan_version`、`step_id`；
- `execution_id`、`attempt_id`、`parent_event_id`；
- `actor`、`source`、`input_digest`、`output_digest`；
- `status`、`reason_code`、`evidence_refs`。

并非每个事件都需要所有字段；适用字段必须存在并通过校验。事件应追加记录，不覆盖历史事实。敏感数据应保存受控引用或摘要，不把密钥、令牌和不必要的原文写入日志。

完整追溯链：

`request → goal interpretation → approach decision → plan version → dispatch authorization → worker execution → tool result → validation → fix/replan attempts → reflection → experience → skill candidate/verification`

## 5. 状态与策略：避免硬编码

生命周期阶段、执行状态、验证结论和任务处置是不同维度，不应塞进一个巨大的 status 枚举。

- **阶段（phase）：** 当前工作处于理解、方法选择、计划、执行、验证、修复、复盘或沉淀的哪个语义阶段。
- **执行状态（execution status）：** pending、ready、running、completed、failed、cancelled 等运行事实。
- **验证结论（verdict）：** pass、fail、inconclusive、blocked。
- **处置（disposition）：** continue、replan、request_input、escalate、stop、complete。

阶段名称和事件类型应版本化；具体任务步骤、工具选择、验收器、重试预算、审批要求和资源限制应来自任务定义、Worker/Capability manifest、租户策略和运行环境配置，而不是写死在核心引擎中。

核心引擎只负责通用合同校验、事件记录、依赖/授权、安全边界、状态转换合法性和证据完整性。它不应内置“自媒体必须先采集评论”或“户型图必须先识别阳台”之类的领域步骤。

## 6. 责任边界

- Planner 提出理解结果、方法和计划，不生成执行成功证据。
- Mission Runtime 校验依赖、租户、授权和运行状态，不替 Worker 编造结果。
- Worker 对局部计划、执行、验证反馈和复盘负责。
- Executor 只报告它实际执行的动作和结果。
- Validator 根据声明的验收合同独立判定，不以执行者自述代替证据。
- Experience Store 保存经过关联和来源校验的事实、复盘和教训。
- Skill Registry 只接收通过独立验证和授权的候选版本。

## 7. 当前代码差距与实施顺序

现有代码已有 Mission Planner、Action Runtime、Worker Handler、任务队列状态刷新、决策追溯、依赖门控、Experience 和 Skill Registry 等基础。但它们尚未组成统一、版本化的员工工作生命周期：

1. Planner 当前仍含内置 `MISSION_KIND_TEMPLATES`；需要逐步转为注册的 Work Type / Worker Manifest / 动态分析结果驱动，保留显式模板作为可配置资产，而非核心引擎内置流程。
2. Mission 计划节点已有 `acceptance`、`validation_checks`、`verification_contract` 等字段，但需要统一到版本化验收合同，并在执行结果后真正调用验证器。
3. 执行、验证、修复、重规划和复盘目前分散在多个运行时；需要通过统一事件和关联 ID 串联，而不是另造一个绕开现有 Mission/Worker 的平行系统。
4. 当前失败学习 ticket 与 Experience 机制需要共享根因、修复 attempt 和验证证据，避免仅保存失败摘要。
5. Skill Replay 尚无专用执行器；在协议、权限和证据链完成前继续 fail closed。
6. 先选一个真实 Worker 任务打通完整链路，再抽象通用机制；不要为了“通用”先实现一套没有真实调用者的空框架。

## 8. 验收标准

生命周期核心可交付的标准：

- 任意 Worker 可基于自己的任务目标和可用能力形成动态计划，不依赖固定领域步骤；
- 每次执行都能关联到计划版本、步骤、员工和任务；
- 验证结论由可追溯证据产生；
- Fail 后能基于根因创建新 attempt 或新计划版本；
- Pass 需要所有必需验收条件通过；
- 阻塞、预算耗尽和人工升级不会被伪装成成功；
- 终态任务有复盘记录，经验可以追溯到原始证据；
- Skill 只有在确有复用价值且通过独立验证时才产生/晋升；
- 现有 Mission/Worker/Experience 数据不因引入新合同而丢失来源和关联。
